# Contact detail and edit

This increment extends the existing admin/owner CRM with a contact detail page and conditional edits. It does not change authentication, provision identities, link contacts to members, add ownership, or implement opportunities. Foundation PRs #85 and #86 are merged.

## API and browser behavior

- GET /api/v1/crm/contacts/{id} returns the existing contact fields plus integer revision and updated_at, and a strong ETag.
- PATCH uses exactly one strong If-Match ETag. It accepts full_name, email, phone and source only. Omitted fields stay unchanged; null clears email or phone; at least one channel must remain.
- Names are trimmed, email is trimmed/lowercased, and phone uses the existing international format. Empty patches, unknown fields, identity/actor injection, invalid JSON, and bodies over 16 KiB are rejected.
- Existing cookie/bearer identity resolution and admin/owner capabilities apply. Cookie mutations require the canonical Origin. All handled responses are private, no-store.
- Errors preserve error text and add code plus optional fieldErrors. Statuses include 400, 401, 403, 404, 412 (stale/different-contact ETag), 413, 415, 428 (missing If-Match), and 503.
- Every accepted PATCH increments revision, including same-value updates. The UPDATE itself filters by ID and expected revision, preventing a read/write race.
- The web form sends only changed fields. A conflict or uncertain save preserves the draft and blocks resubmission until the user loads and explicitly reviews the latest details. Reviewing retained edits preserves newer changes to fields the user did not edit.

Contact IDs identify CRM people. Application IDs identify the authorized actor. Email and phone do not establish identity ownership or grant access.

## Migration and compatibility

The additive migration is supabase/migrations/20261017232622_crm_contact_edit.sql, generated by Supabase CLI. Apply after the foundation contact migration. Existing rows start at revision 1 with updated_at equal to created_at. Subsequent updates stamp revision and updated_at in a SECURITY INVOKER trigger; the API supplies updated_by.

The server retains SELECT/INSERT and gains column UPDATE only for full_name, email, phone, source and updated_by. It cannot update ID, revision, timestamps or creation actor, or delete/truncate contacts. Direct anon/authenticated access remains revoked and RLS remains closed. The trigger function has no public/client execution grant. The old migration is unchanged.

List/create response shapes and the existing Swift models remain unchanged. Native editing can later consume the detail contract and add If-Match support through a coordinated change to the shared request helper. One unified Swift app remains the release target.

## Verification

Local unit/SQL/contract tests: 210 passing. TypeScript and the production build pass. Lint has four existing warnings and no errors. The build uses nonfunctional placeholder configuration, not production credentials.

The real integration workflow explicitly copies only the foundation and contact-edit migrations into its disposable Supabase fixture. It checks the CLI migration ledger, RLS, column/function privileges, real cookie/bearer authorization, browser edits, normalization/validation, immutable fields, simultaneous writes, unchanged identity links, two-editor conflict recovery, and an accepted save whose response is lost. OpenAPI schemas validate fixtures and live responses. Auth credentials remain ephemeral, with traces/videos/screenshots disabled.

To reproduce the integration suite, follow docs/crm-staging-verification.md in an isolated checkout with Docker, adding the contact-edit migration to the explicit copy list before the local CLI push. Do not run root db push or use hosted preview databases for fixture writes.

GitHub integration and Swift CI evidence will be recorded on the draft PR. Local checks do not establish hosted staging, production schema parity, native authenticated UI, or physical-device readiness.

Native session/UI and physical-device checks remain separate gates. No production migration, identity mutation, real messaging, Twilio routing, or Fuelwise change is part of this increment.
